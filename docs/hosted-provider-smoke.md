# Optional hosted-provider smoke test

This procedure is manual and optional. It uses the operator's native Pi and Codex configuration and is excluded from CI because CI must not use public networks, hosted services, or credentials.

1. Use disposable low-cost provider accounts, non-sensitive Markdown and standalone HTML fixtures, and creator context. Do not use production capability URLs, private source, personal data, or secrets. Use a restrictive Codex approval policy and sandbox suitable for untrusted whiteboard input.
2. Authenticate with Pi and Codex through each provider's native CLI flow. Do not pass API keys or tokens through Agent Whiteboard flags, environment variables, prompts, or logs.
3. Enable `viewer.local_agent.enabled`, add the exact HTTPS publishing origin with `agent-whiteboard agent trust add`, and start the publishing server and `agent-whiteboard agent serve`.
4. In current Chrome, open each Markdown and HTML capability, grant Local Network Access if prompted, inspect the Page context disclosure, and switch between Pi and Codex before connecting. Confirm that selection alone produces no hosted request and sends no page content.
5. Confirm the viewer and broker negotiate local API version 5 and WebSocket subprotocol `agent-whiteboard.v5`. Confirm a new provider turn uses native envelope v4. If browser and broker are incompatible, deploy both together, clear only disposable local broker conversation/workspace state, and restart the foreground broker or managed daemon; do not continue with mixed versions or delete public whiteboards/provider-native histories.
6. Select Pi and connect on Markdown. Drag across part of a paragraph and use **Add to message**, add a heading section, and type text before, between, and after both inline tokens. Send it and confirm the displayed and provider-received message preserves that exact order while the provider turn also contains the complete Markdown/context envelope. Activate a sent token and confirm the viewer returns to the matching source.
7. On HTML, use a head-first fixture containing unique, labeled examples of every component kind: section, image/figure, SVG or canvas chart, table, `pre > code`, blockquote/note or alert, and one explicit custom component. Confirm excluded content is absent. Hover each kind and confirm the compact parent-owned action reads exactly **+ Add** while its accessible name includes the type and label. Add multiple components with reader text before, between, and after them; send and verify exact ordering, bounded semantic excerpts, complete exact HTML/context authority, and revision-bound navigation from sent tokens.
8. Open the app-bar **Components** chooser and add components with the keyboard. Repeat with touch or coarse-pointer emulation and confirm the chooser remains usable without hover. Self-navigate the child or otherwise use a bridge-missing fixture and confirm the chooser still adds canonical components while no hover hint appears. With disposable trusted publisher code, withhold or emit malformed/stale/unknown candidate messages and attempt a message containing a transferred `MessagePort`; confirm none creates or submits a reference, no broker/context data reaches the child, and the chooser continues to work.
9. Include exactly one eligible exact-source embedded PNG/JPEG/GIF/WebP `<img>` component. With an image-capable model, confirm **+ Add** produces one ordered component token and one private inline visual rather than an attachment or public Whiteboard image. Repeat with unavailable image capability and confirm the semantic reference still works without a visual. Confirm SVG/canvas, remote/blob/runtime images, responsive image alternatives, video/audio, live state, and non-image kinds never claim or capture runtime pixels.
10. With a disposable PNG or JPEG, exercise ordinary multi-file selection, image paste, remove, and an image-only submit. Also select a rendered same-origin Markdown image with **Add image** and confirm it appears inline rather than in the attachment tray. Confirm preparing/ready previews, the sent preview, a queued image preview during an active response, and restored history after reconnect. If the selected model reports no image support, confirm image controls are unavailable while text and semantic HTML components remain usable. Do not weaken Pi's native image policy for this check.
11. For both providers, switch between Pi and Codex before and after connecting and confirm selection is silent, conversations remain independent, and inactive work is not interrupted. Open the shared composer pill and choose a visible model and supported effort. Confirm Pi omits Speed and Codex offers Standard/Fast only when advertised. Send different non-sensitive messages and confirm each provider receives the exact selected tuple; changing Pi also updates its future native default without changing already-running Pi sessions. Confirm image availability follows the selected model and no private path appears in the browser.
12. If the effective Codex configuration makes a harmless command, file change, permission request, or MCP elicitation available, exercise one request without using sensitive data. Confirm bounded tool activity appears, the interactive response reaches App Server, and a second attached tab becomes read-only after the first valid response wins. Do not expect a Page Agent prompt when the effective approval policy does not request one.
13. Do not test `request_user_input` as part of this stable smoke test. It is an experimental App Server API and Agent Whiteboard leaves `experimentalApi` disabled.
14. With disposable non-sensitive native skills for each provider, type `$`, select and submit them alone and with text. Confirm Pi enforces its one-skill limit, Codex honors its advertised multiple-skill limit, and no skill path or body appears in browser frames or DOM. Exercise a Pi multiline extension interaction and repeated passive notices; confirm adjacent duplicates coalesce and successful response means the complete record was written before its local deadline, not that Pi acknowledged consuming it.
15. Run exact `/compact`, confirm `Compacting context…` then `Context compacted`, and repeat with Stop to confirm `Stopping…` then `Compaction stopped`. During an active Codex turn, prepare a next draft and press Enter; confirm no follow-up command or queue row appears, Stop preserves the draft, and Pi still queues normally under the equivalent Pi flow. During active Pi and Codex work, confirm Escape performs the same interruption as Stop without closing Page Agent.
16. After one accepted turn for each provider, reload and open a genuinely new whiteboard from the same publishing origin. Confirm that provider's last accepted tuple initializes it, while an existing or restored conversation retains its own effective native tuple and an unsent menu edit disappears on reload. Send a continuation for each provider and confirm unchanged page context is not resent. Interrupt a separate test turn and confirm it is not automatically replayed. A Codex App Server failure may interrupt every active Codex turn, but Pi remains independently available.
17. Exercise New, archive restore, and archive deletion for each provider only with disposable sessions. Confirm that Codex New uses the currently visible pill, archives remain provider-specific, restored Codex settings override browser preference, attachment previews restore, and archive deletion removes the disposable image workspace before removing local test state.
18. Stop the broker, delete the disposable whiteboard and local test sessions, and remove the test origin from the trust list if it is no longer needed.

Do not capture provider request bodies, auth files, transcripts, capability IDs, model output, tool details, or approval payloads in shared logs or bug reports. Record only sanitized pass/fail observations and version information. This smoke test does not establish a content-only boundary: tool allowlists, per-whiteboard filesystem roots, and a stronger cross-agent sandbox are deferred.
